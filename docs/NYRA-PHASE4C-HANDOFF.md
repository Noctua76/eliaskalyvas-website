# Phase 4C handoff — proposal only, no activation authorization

Phase 4B keeps normal `npm run build`, the current Pages workflow and production Signals indexability unchanged. Completing the following gates needs external technical/visual review and specific approvals; passing a synthetic test is not permission to publish.

1. **Review the exact Phase 4B diff and delegated materialization mapping.** Retain v1.1 unchanged. Confirm that a held Phase 2 proposal is private intent evidence, every new candidate derives from the same exact owner approval, and abandoned candidates are never rewritten or falsely promoted into verified history. Resolve any required contract incompatibility before further integration.
2. **Native PostgreSQL/Supabase acceptance.** Use an approved disposable local Docker/Supabase stack or separately approved staging resources. Run native SECURITY INVOKER/RLS/ACL checks, actual signed Auth tokens and MFA current/next AAL2, owner revocation, session deletion/expiry/downgrade, PostgREST service-role behavior, duplicate approval and independent-connection locking/deadlock/retry cases. Run security advisors. The optional native script exercises a disposable native SQL cluster only; it is not GoTrue/MFA proof. Apply no production migration until these pass.
3. **Package actual Edge runtime.** Include the unchanged JSON schema files in the required relative static-file layout, pin npm resolution to existing Ajv and verify target Edge runtime imports, Node compatibility and explicit permissions. Do not infer platform compatibility solely from local Deno 2.9.6. Mount no private route until exact-token owner authorization, service-only RPC access and machine/browser separation are verified end to end.
4. **Approve Storage/inspector design.** Only after separate approval, create/configure a private bucket and the minimum private server integration. The checked Node Sharp inspector is not native Edge Sharp. Choose an approved supported inspection service/job/attestation boundary, bind its result to exact actual bytes, and require the existing owner/MFA rights review. Reuse all Phase 3 privacy/MIME/decode tests. Keep raw notes/evidence and service credentials out of browser, runner and public outputs. Test object collision, orphan reconciliation and denied public bucket settings.
5. **Register attempts server-side from trusted GitHub facts.** Do not accept caller release/generation/rollback selectors. Persist the run/attempt/check-run/SHA identity, synchronize the complete owner-approved outbox, acquire a lease/fence and materialize only that scope. Establish the initial known empty/no-publication baseline by independent observation, without fabricating a success receipt. Implement lease heartbeat/upper bounds if actual build duration needs it; expired/unknown work must reconcile before reuse.
6. **Restructure the workflow only in a separately reviewed PR.** The current build job has no protected environment, so its context must never be accepted as an export requester. A compatible future layout is an unprivileged trigger/orchestrator plus a pinned reusable **single protected delivery job** that performs export → approved build → artifact sealing/attestation → fresh-token permit → Pages deploy. Put `environment` on the actual job inside the reusable workflow, not merely on its caller or a later deploy job. Keeping export/permit/deploy in that same job matches Phase 4B's exact registered check-run identity. Splitting them into multiple security contexts would require separately reviewed per-stage identities/policies and registry changes; do not relax job matching to make it work.
7. **Future GitHub protections and permissions.** Restrict the protected delivery environment (for example the separately reviewed `github-pages` environment) to the approved main branch. Require branch/ruleset review/status checks for workflow/runtime changes, protect against direct/force pushes, pin reusable workflow and third-party actions to approved immutable SHAs, use read-only PR/fork permissions and never `pull_request_target` to authorize export. Move OIDC and Pages write permissions from workflow-wide inheritance to only the protected delivery job. Configure repository-wide concurrency shared by publication and ordinary website rebuilds, with `cancel-in-progress: false`; never cancel an in-flight deploy and infer non-delivery. Normal code rebuild/rollback must obtain the current authorized dataset rather than an old public artifact.
8. **Pin exact OIDC policy before enabling endpoints.** Verify immutable repository/owner IDs, exact audience, issuer, branch, subject format, caller workflow/ref, reusable workflow/SHA, environment, allowed event and actual REST job name in an explicitly approved isolated environment. GitHub supports both legacy and immutable-ID subject formats; do not guess or accept wildcard/fallback subjects. The verifier requires `check_run_id`, `job_workflow_ref` and `job_workflow_sha`; the future job must actually supply them. A fresh token/jti is required for export and permit. No production token was issued in Phase 4B. Any new GitHub App/server credential, custom protection or staging resource needs separate approval.
9. **Preserve one owner action.** The existing owner confirmation remains the only editorial publication authorization. Outbox/worker/dispatch retries must be automatic and idempotent, not a second Publish approval. Environment branch protections and the trusted server intent check must enforce the security boundary. If policy requires an additional manual GitHub environment approval, explicitly resolve that conflict with the single-action requirement before activation; do not silently introduce another owner click.
10. **Artifact provenance and deployment permit.** Build from the registered code SHA and authenticated current dataset; do not let a general file/env JSON loader confer authority. Use only the sealer's retained exact public files. Phase 4B's `artifact_sha256` is the deterministic sorted public-file inventory digest, not GitHub's ZIP digest. The real uploader/observer must bind that inventory to the actual GitHub artifact ID and archive attestation. Remove build-side rights proofs, private capabilities and any input-only metadata before uploading public Pages artifacts. Immediately before deploy, verify the exact candidate/source generation/fence/expiry/code/manifest/artifact permit. No production permit consumer/uploader is implemented here.
11. **Independent live observations and receipts.** Add a narrowly scoped public manifest witness/marker only after separate review. The trusted observer must correlate GitHub run/attempt/code/deployment result and actual public manifest plus all required canonical routes/assets, without trusting runner “success” JSON. Receipt requested/completed/observed times must match independently obtained facts. Enforce unchanged F01 transition evidence and 15/30-minute windows. Unknown delivery blocks retries. Proven never-deployed work can receive a fresh attempt/candidate; actual delivered bytes must never be retimestamped. Confirmed late publication gets a timing exception, preserved dates and explicit operational reconciliation of the observed baseline—not a fabricated normal receipt.
12. **Failure and activation acceptance.** Test publish/replace/withdraw/rollback independently in GR and EN; simultaneous owner edits/authorizations, stale generations, failed artifact upload, canceled/expired jobs, replay, unknown results, restart recovery, delayed caches and real withdrawal removal. Test ordinary site rebuild and code rollback against current active content. Repeat preview/no-JS/browser and all protected home/Hero/favicon/booking/legal regressions. Only external approval of exact migrations, routes, protections, provenance and a real first publication authorizes rollout.

No server client, credential, OIDC token, export URL, dispatch, live verifier, bucket or new workflow is provisioned by this document. No Phase 4C implementation is included in Phase 4B.
